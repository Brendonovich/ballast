# 0005 — Generic webhooks through the cloud relay

*Status: proposed · 2026-11-23 · effect `4.0.6` · agent driver implemented, cloud side not yet
implemented*

## Context

`@ballast/module-http` needs a webhook integration for providers that only support
"paste a URL" callbacks (Ko-fi, Streamlabs, StreamElements, custom alert boxes). A desktop
machine is not publicly reachable, so the same hook must work in two modes:

| Mode | Listener | URL | Use |
|---|---|---|---|
| **Local** | `@ballast/module-http/driver` binds an HTTP listener on the machine (localhost or LAN) | `http://192.168.1.20:8787/hooks/kofi` | Provider can reach the LAN, or testing |
| **Cloud** | The Ballast Worker receives the request and relays it to the paired machine over the existing relay WebSocket | `https://<cloud>/hooks/<machineId>/<hookId>` | Public incoming webhooks |

The script-facing API is identical: `Http.Webhook("kofi")` declares an `either`
connection, and `Http.Webhook.subscribe(name, hook, handler)` records an
`http/webhook` topic.
The manifest's connection location and the user's connection configuration choose the
transport.

The agent-side driver is implemented in `packages/integrations/http/src/driver`. This
record specifies exactly what the cloud must add; the driver is written against these
shapes and is tested with a mock relay and a real relay WebSocket in
`packages/integrations/http/test/{webhook,relay}.test.ts`.

## Decision

### 1. Terminology and identity

- A **hook** is a pair `(machineId, hookId)`.
- `machineId` is the existing machine id from pairing (decision 0002). It is not a secret.
- `hookId` is an unguessable, URL-safe random id generated by the agent (or cloud UI) when the
  user configures a connection: 32 random bytes, base64url, 22–64 characters. It is a bearer
  capability: anyone with the complete URL can post to it. Treat it like a webhook secret.
- The public URL is `POST /hooks/:machineId/:hookId`. Other methods are accepted too; the
  provider's method is passed through to the handler. There is no machine or user auth header
  on this route; the unguessable hook id is the capability, and optional verification is
  enforced at the edge (below).
- Hook ids are unique per machine. The Worker must reject malformed ids and unknown pairs
  with a generic `404` (do not reveal whether the machine or the hook is missing).

### 2. Connection configuration (agent side)

```ts
interface WebhookDefinition {
  slot: string;                    // script slot, e.g. "kofi"
  hookId?: string;                 // required for cloud; local defaults to slot
  transport: "local" | "cloud";
  verification?: WebhookVerification;
  response?: WebhookStaticResponse;
  maxBodyBytes?: number;           // default 64 KiB
  local?: { host?: string; port: number; path?: string }; // path default /hooks/<slot>
  cloud?: { label?: string; maxAgeMs?: number; onStale?: "drop" | "deliver" };
}
```

Verification is declared only in connection config, never in a script:

```ts
type WebhookVerification =
  | { type: "shared-secret"; header: string; secret: string }
  | { type: "hmac-sha256"; header: string; secret: string; encoding: "hex" | "base64";
      prefix?: string;            // e.g. "sha256=", stripped before comparison
      timestampHeader?: string;   // when set, sign "<timestamp>.<raw body>"
      toleranceSeconds?: number } // default 300
```

The static response is what the sender receives:

```ts
interface WebhookStaticResponse {
  status?: number;                // default 204
  body?: string;
  headers?: Record<string, string>;
  contentType?: string;           // default text/plain; charset=utf-8 when body is present
}
```

### 3. Registration API

The agent registers cloud hooks after the relay/machine token is available. The machine API
uses the existing `Authorization: Bearer blst_m_…` machine token.

#### `POST /api/hooks/register`

Replaces the **complete set** of cloud hooks for the calling machine. Hooks absent from the
body are unregistered (and stop receiving deliveries). The operation is idempotent. The agent
calls it once when it starts the cloud webhook driver and again after a manifest/connection
change.

```json
{
  "hooks": [
    {
      "hookId": "N3x…22-43-chars…",
      "label": "Ko-fi",
      "maxAgeMs": 60000,
      "onStale": "drop",
      "verification": {
        "type": "hmac-sha256",
        "header": "x-kofi-signature",
        "secret": "…",
        "encoding": "hex"
      },
      "response": { "status": 200, "body": "ok" }
    }
  ]
}
```

Response `200`:

```json
{ "hooks": [ { "hookId": "N3x…", "url": "https://cloud.example/hooks/m_abc/N3x…" } ] }
```

Validation and storage:

- `hookId` must match `^[A-Za-z0-9_-]{22,64}$`; duplicate ids in one request are rejected.
- `maxAgeMs` must be 0–86_400_000; `onStale` defaults to `drop`, `maxAgeMs` to 60_000.
- `response.status` must be 200–299 (a provider-facing success status), default 204;
  `response.body` ≤ 4 KiB; headers ≤ 32 entries and no CR/LF.
- The verification secret is sealed with the existing token-vault key (AES-256-GCM) before it
  reaches D1. It is never returned by any API and never logged. Non-secret configuration is
  stored as JSON alongside the sealed secret.
- Registration rows survive agent disconnects and restarts. They are deleted explicitly by
  unregister, by the full-set replace, or by a retention job (default 90 days without a
  register call). A machine's hooks are not deleted on machine unpair until the user confirms,
  because a provider may still be retrying.

#### `POST /api/hooks/unregister`

```json
{ "hookIds": ["N3x…"] }
```

Idempotent; returns `204`. Unknown ids are ignored.

Optional: `GET /api/hooks` returns the machine's registered hooks (without secrets, with
URLs) for the connection settings UI.

### 4. Public ingress

#### Route

```
POST /hooks/:machineId/:hookId
```

Any method is accepted (GET, POST, PUT, PATCH, DELETE, HEAD). The raw request body and
headers are forwarded unchanged except for Cloudflare hop-by-hop headers. There is no CORS
preflight requirement for server-to-server providers; respond to `OPTIONS` with the configured
static response (or 204) so browser test tools are not blocked.

#### Processing

1. Validate `machineId` and `hookId` shape, then look up the hook in D1. Unknown → `404`.
2. Apply rate limits (below). Limited → `429` with `Retry-After`.
3. Read the raw body, capped at `maxBodyBytes` (default 64 KiB, absolute cap 1 MiB).
   Larger → `413`; do not buffer unbounded data.
4. If the hook has `verification`, verify at the edge:
   - **shared-secret:** constant-time compare of the configured header with the stored secret.
   - **HMAC-SHA256:** constant-time compare of the header (after optional `prefix`) with
     `HMAC(secret, rawBody)` or `HMAC(secret, timestamp + "." + rawBody)` when
     `timestampHeader` is set; reject a timestamp outside `toleranceSeconds` (replay window).
   - Missing or wrong verification → `401`. Never relay an unverified body.
5. Assign a `deliveryId`. The agent-generated delivery id is random; no provider dedupe is
   promised at the edge because providers differ. Optionally, a future provider-specific
   adapter can supply a stable id.
6. Enqueue a `webhook_delivery` entry in the machine's Relay DO (same seq space as events;
   see §5).
7. Immediately return the hook's stored static response. The cloud never waits for the
   desktop handler.

#### Responses

| Condition | Response |
|---|---|
| Accepted and enqueued | Stored static response (default `204`, body/headers from config) |
| Verified but body over limit | `413` |
| Verification missing/wrong | `401` |
| Malformed/unknown hook | `404` |
| Rate limit | `429` + `Retry-After` |
| Relay DO unavailable | `503`; the provider may retry (do not return success) |

Because the desktop is not in the request path, **cloud webhooks support static responses
only**. A handler cannot change the status/body. This is deliberate: the event bus is
one-way and at-least-once; a cloud request cannot wait for a worker handler that may be
offline, restarting, or slow. Local listeners could in principle support a handler response
by adding a request/response delivery primitive to `@ballast/core` (for example
`EventHost.deliver(event, { timeoutMs })` returning a response and the driver awaiting it),
but that is a core change and is not part of v1. Local mode therefore also uses the static
response for consistency.

### 5. Relay frame and buffering

#### `packages/cloud-protocol` additions

```ts
export const WebhookVerification = Schema.Union([
  Schema.Struct({
    type: Schema.Literal("shared-secret"),
    header: Schema.String,
    secret: Schema.String,
  }),
  Schema.Struct({
    type: Schema.Literal("hmac-sha256"),
    header: Schema.String,
    secret: Schema.String,
    encoding: Schema.Literals(["hex", "base64"]),
    prefix: Schema.optionalKey(Schema.String),
    timestampHeader: Schema.optionalKey(Schema.String),
    toleranceSeconds: Schema.optionalKey(Schema.Number),
  }),
]);

export const WebhookStaticResponse = Schema.Struct({
  status: Schema.optionalKey(Schema.Number),
  body: Schema.optionalKey(Schema.String),
  headers: Schema.optionalKey(Schema.Record(Schema.String, Schema.String)),
  contentType: Schema.optionalKey(Schema.String),
});

export const WebhookRegistration = Schema.Struct({
  hookId: Schema.String,
  label: Schema.optionalKey(Schema.String),
  maxAgeMs: Schema.optionalKey(Schema.Number),
  onStale: Schema.optionalKey(Schema.Literals(["drop", "deliver"])),
  verification: Schema.optionalKey(WebhookVerification),
  response: Schema.optionalKey(WebhookStaticResponse),
});

export const RegisterHooksRequest = Schema.Struct({
  hooks: Schema.Array(WebhookRegistration),
});
export const RegisterHooksResponse = Schema.Struct({
  hooks: Schema.Array(Schema.Struct({ hookId: Schema.String, url: Schema.String })),
});
export const UnregisterHooksRequest = Schema.Struct({
  hookIds: Schema.Array(Schema.String),
});
```

A relayed delivery is a **new server→agent frame** on the existing relay socket:

```ts
export const WebhookRelayDelivery = Schema.Struct({
  hookId: Schema.String,
  deliveryId: Schema.String,
  method: Schema.String,
  path: Schema.String,
  query: Schema.Record(Schema.String, Schema.String),
  headers: Schema.Record(Schema.String, Schema.String),
  bodyBase64: Schema.String, // standard base64; binary safe; ≤ 1 MiB
  receivedAt: Schema.Number, // Unix ms, when the Worker accepted the request
});

export const RelayWebhookDelivery = Schema.Struct({
  _tag: Schema.Literal("webhook_delivery"),
  seq: Schema.Number,
  stale: Schema.Boolean,
  delivery: WebhookRelayDelivery,
});

// RelayServerMessage union gains RelayWebhookDelivery.
// RelayClientMessage is unchanged: ack/pong already cover it.
```

The agent acknowledges `seq` with the existing `{ "_tag": "ack", "seqs": [...] }` frame.
No new client→server registration frame is needed: registration is the HTTP API in §3.

#### Buffer semantics (reuse the event relay)

- One Relay DO per machine, one monotonically increasing `seq` for events **and** webhook
  deliveries. The existing hello/replay/ack path and ordering guarantees apply unchanged.
- A delivery is buffered until acknowledged, with the manifest's `maxAgeMs` and `onStale`
  (defaults 60_000 ms and `drop`). On first send after reconnect:
  - fresh: `stale: false`;
  - older than `maxAgeMs` and `onStale: "drop"`: mark dropped, never send, keep it for the
    inspector until retention;
  - older and `onStale: "deliver"`: send once with `stale: true`.
- Retention: 24 h and 1,000 entries per machine, as for events. Evict the oldest first.
- While the agent is offline, deliveries accumulate (subject to retention/limits). If the
  provider retries, each accepted request is a separate delivery; the handler must be
  idempotent or the user must configure provider-side retry suppression.
- The agent acks after handing the delivery to its event bus (the driver enqueues it and the
  agent adapter publishes to the bus). A crash after ack but before the script handler runs
  loses that delivery; this is the same at-least-once boundary as Twitch/EventSub and is
  acceptable for v1. The event inspector can replay it later.
- Local mode has no relay: the listener delivers directly to the driver queue with no
  buffering across process restarts. The same `maxAgeMs`/`onStale` values are still recorded
  in the manifest for the bus's freshness policy.

### 6. Limits and abuse control

| Limit | Default | Notes |
|---|---|---|
| Raw body | 64 KiB per hook | Absolute cap 1 MiB; reject before buffering |
| Headers | 32 KiB total | Cloudflare also caps header size |
| Static response body | 4 KiB | Stored in D1/DO, not generated per request |
| Hook id | 22–64 base64url chars | Unguessable; treat as a secret |
| Requests per hook | 60/min per machine | Fixed-window counter in the DO (hot path) |
| Requests per machine | 600/min | Across all hooks |
| Requests per client IP | 120/min | Worker-level D1 fixed window, best-effort behind Cloudflare |
| Registered hooks per machine | 32 | Enough for every integration slot |
| Buffer | 1,000 entries / 24 h | Shared with events |
| Registration calls | 30/min per machine | Protects D1 |

Rate-limit keys include the hook id and machine id so one leaked URL cannot exhaust another
machine's budget. Return `429` with a small `Retry-After`; do not reveal whether a hook exists
when limiting an unauthenticated caller (use the same 429/404 shape as unknown hooks where
possible). Cloudflare-level rules should sit in front of the Worker for volumetric attacks.

### 7. Verification at the edge vs at the agent

- **Edge verification is authoritative for cloud hooks.** It rejects forged requests before
  they consume relay buffer or reach the desktop, and it is the only place the secret is
  needed besides the agent's connection config.
- The secret is sent to the cloud only on `POST /api/hooks/register` over TLS, is sealed at
  rest, and is never returned. The agent may keep its own copy in connection config and
  re-verify a relayed delivery (the driver does when `verification` is configured). This
  defense-in-depth check is optional: a cloud hook can omit the agent-side secret if the
  config only stores it in the cloud. The driver currently keeps both, because the same
  connection config is also usable for local mode.
- **Local hooks verify only at the agent.** They are not routed through the cloud.
- Timestamp checks are optional but recommended when the provider sends a timestamp header;
  without one, a captured request can be replayed. The unguessable URL plus a shared secret is
  the baseline.

### 8. Agent-side implementation (already in this repo)

`packages/integrations/http/src/driver`:

- `WebhookDriver` — `start(definitions)` opens grouped local `NodeHttpServer` listeners
  (one server per `host:port`, routes by path), verifies requests, enqueues
  `WebhookDelivery` values and returns `{ deliveries, statuses, close }`.
- `WebhookRelay` — `register`/`unregister` call the HTTP API above; `deliveries` is a
  reconnecting WebSocket client for `/relay/:machineId` that decodes
  `webhook_delivery` frames, answers `ping` with `pong`, and acks the seq after enqueueing.
- `packages/integrations/http/test/webhook.test.ts` covers local shared-secret/HMAC
  verification, static 200/204 responses, delivery to the handler queue, cloud registration
  and relayed delivery with a mock relay.
- `packages/integrations/http/test/relay.test.ts` covers the proposed frame shape and a real
  mock WebSocket relay (hello/ping/delivery → pong/ack).

### 9. What the cloud agent must implement

1. Add the schemas above to `packages/cloud-protocol` and extend `RelayServerMessage`.
2. D1 migration `webhook_hooks`: `(id, machine_id, hook_id, label, verification_json,
   secret_ciphertext, secret_iv, response_json, max_age_ms, on_stale, created_at,
   updated_at)`, unique `(machine_id, hook_id)`, index on `(machine_id)`.
3. `POST /api/hooks/register` and `/api/hooks/unregister` with machine auth, validation,
   full-set replace, sealing via the existing vault, and rate limiting.
4. `POST /hooks/:machineId/:hookId` (and other methods) with lookup, verification, body
   limits, rate limits, static response, and enqueue into the Relay DO.
5. Relay DO: accept a `webhook` buffer entry alongside events; share seq/ack/hello/replay;
   apply `maxAgeMs`/`onStale`; expose it to the inspector; include it in the Inspector/replay
   API when that lands.
6. Tests with a real signed request → D1 hook row → relay DO → agent WebSocket ack, mirroring
   the Twitch EventSub ingress tests in decision 0002.

### 10. Open questions

1. **Hook id generation:** agent-generated (current driver) vs cloud-generated during
   connection setup. Agent-generated lets the same config work offline and in local mode, but
   the cloud must accept client-provided capabilities. Accept client-provided ids in v1.
2. **Provider-specific dedupe.** Generic webhooks have no standard delivery id. A later
   adapter could map `X-Kofi-Message-Id` etc. to delivery ids. Until then, duplicates are
   possible on provider retry and relay replay.
3. **Inspector and replay UI.** The relay keeps deliveries for 24 h; expose them like events
   once the inspector has a machine-authenticated history API (0002 §8).
4. **Multiple machines per user.** The URL embeds one machine id; a hook belongs to one
   machine. If multiple machines must receive one webhook, the cloud needs fan-out, which is
   out of scope.
5. **Handler-generated responses.** Requires a request/response event delivery in core, plus a
   timeout and an explicit opt-in (local only at first). Not in v1.
